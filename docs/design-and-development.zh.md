# EduEval Studio：从“跑几个模型”到一条可复查的评测证据链

## 一、为什么做这个插件

最初的需求很直接：把同一批教学任务交给几个模型，看看谁写得更好。

但真正开始做之后，问题很快出现了。模型回答只是最表层的结果，下面还有一长串需要被固定下来的东西：题目是什么、评分标准是什么、由谁评、按什么规则算分、失败怎么处理、人工判断和模型判断是否一致、下一次还能不能复现。

如果这些环节散落在聊天记录、临时脚本和几张截图里，所谓“评测”很快就会变成一次性的演示。换一道题、换一个模型、换一个人评分，结论就可能完全不同。

EduEval Studio 想解决的不是“让模型生成一段教案”，而是把一次模型评测做成**一条可复查的证据链**：

```text
Query → Generation → Rubric Judge → Blind Human Review → Report
```

每一环都留下记录，每一个分数都能追溯到题目、评分维度、证据和模型身份。插件最终以原生 DSH 面板的形式运行，而不是一个独立网页或 iframe。它应该像 DSH 自带的功能一样被打开、使用、保存和卸载。

## 二、设计理念

### 1. 原生集成，而不是“嵌一个网页”

EduEval Studio 通过 DSH 的 `main` 面板和 `sidebar.panellist` 注册界面，使用 DSH 的认证 Fetch 路由和凭据服务。它不启动自己的服务器，不打开 iframe，也不要求用户离开 DSH 去另一个地址操作。

这样做的代价是必须遵守 DSH 的 Host/Client 边界；收益是插件能真正进入用户的工作流，而不是一个看起来很像插件的演示页。

### 2. 评测是一条链，不是一张排行榜

排行榜很直观，但排行榜只回答“谁排第一”，不回答“为什么”。

因此插件把一次 Run 拆成几个可以独立检查的对象：

- 这一轮用了哪些题目，题目是否被编辑过；
- 每个模型看到的 Query 是否完全一致；
- 每道题的 Rubric 权重是否合计 100%；
- Judge 是否给出了每个维度的分数、证据和理由；
- 哪些任务是生成失败、评分失败或被取消；
- 人工盲评看到了什么，揭盲后和 Judge 差多少。

排行榜只是链条末端的视图，不是整个系统。

### 3. 题目与评分标准同源

每道题自带 6 项 Rubric，包含维度名称、权重、满分判据和 Critical Errors。题目可以编辑，Rubric 也可以编辑，但 Run 会保存当时的快照。

这意味着：

- 改题不会悄悄改掉历史结果；
- 同一道题的不同模型回答，使用同一套评分标准；
- 评分维度不是 Judge 临场发挥，而是题目定义的一部分；
- Critical Error 单独记录，不会被静默折算成一个普通低分。

### 4. 可比较，比“看起来专业”更重要

多模型评测最容易犯的错误，是把不同题目、不同评分标准、不同失败处理方式的结果放在一起比较。

EduEval Studio 的几个约束都是为了可比性：

- 同一 Run 内，所有模型使用同一批 Query；
- 排名使用所有模型都成功评分的**共同样本**；
- 覆盖率单独展示，失败不进入分母，也不伪装成 0 分；
- 每个模型保存自己的 Base URL、Model ID、Key 引用、温度和超时；
- Judge 独立配置，不复用被测模型的 Key。

这些约束不会让结果更“好看”，但会让结果更接近可以讨论的事实。

### 5. 人机互补，而不是用 Judge 替代人

LLM-as-a-Judge 能扩展评测规模，但它有偏差，也会受提示词、模型版本和评分标准清晰度影响。

所以插件把人工盲评放在同等重要的位置：

- 评审前只显示匿名 A/B/C，不把模型名和厂商下发给浏览器；
- 人工逐项打 0/1/2，可以写文字评价；
- 保存人工评分后才允许揭盲；
- 看板展示人工总分、Judge 总分、MAE、逐项一致率和 Spearman 相关。

Judge 负责规模，人负责校准。两者不是替代关系。

### 6. 本地优先，密钥不进入浏览器

模型调用、评分、盲评映射都在 Host 端完成。浏览器不会收到 API Key，也不会在评审前收到模型身份。

API Key 使用 DSH 凭据服务保存，配置文件和导出文件里不写明文 Key。Key 引用使用 `EDUEVAL_` 命名空间，避免覆盖用户已有的 `DEEPSEEK_API_KEY` 等凭据。

评测数据默认写入 `$DSH_HOME/edueval`，采用原子写入。卸载插件不会删除评测历史；只有用户明确清理数据目录时才会删除。

### 7. 界面要克制

评测界面容易堆满解释文字：每个按钮下面一段说明，每个字段下面一行提示，最后用户反而不看主要内容。

最终的界面刻意做了减法：删除灰色说明性小字、卡片描述、字段 hint、协议说明框和重复的模型元信息，只保留字段名、按钮、状态、分数、表头和必要标签。

信息应该出现在它该出现的位置，而不是靠一层层小字解释。

## 三、一次评测如何运行

1. **选择题目**：使用内置的 10 题 Benchmark，或导入 JSONL/CSV，手动新增、编辑和筛选。
2. **配置模型**：在“测试模型 1 / 2 / 3”中选择厂商，自动填充 Base URL、Model ID 和 Key 引用，也可以全部手动修改。
3. **配置 Judge**：单独选择 Judge 模型、Base URL、Key 引用、温度和超时。
4. **运行**：只生成回答，或生成后自动评分；支持并发、重试、取消、继续缺失任务和重试失败任务。
5. **人工盲评**：对匿名候选逐项评分，保存后揭盲。
6. **查看与导出**：共同样本排行榜、维度对比、失败案例、Critical Errors、人工一致性；导出 CSV、JSON 或 Markdown。

每一步都写入同一个 Run，刷新页面或重启 Host 后仍可恢复。

## 四、开发过程

### 第一阶段：确定边界

先把“插件”与“网页”区分清楚。插件必须是 DSH 的原生 Bundle，具备：

- Host 端入口和 Client 端入口；
- `main` 槽与侧边栏图标；
- 认证 Fetch 路由；
- DSH 凭据服务接入；
- 可安装、可卸载、可升级的 npm 包结构。

这一阶段最重要的不是写界面，而是确定哪些东西必须留在 Host：密钥、模型调用、评分计算、盲评映射、持久化。

### 第二阶段：先定数据，再做页面

在写 UI 之前，先确定 Benchmark 的字段、Rubric 的结构、Run 的状态机、失败和重试的语义。

题目字段包括：ID、学段、年级、学科、主题、难度、任务类型、Query、6 项 Rubric、Critical Errors。

Run 保存题目快照、模型快照、Judge 配置快照、每个任务的尝试次数和错误、评分结果与用量。这样页面只是数据的视图，而不是数据的唯一来源。

### 第三阶段：把模型适配器做薄

所有厂商都走 OpenAI-compatible `/chat/completions`，但每家仍有差异：Base URL、模型 ID、Key 格式、是否支持 `max_tokens`、思考模型如何消耗 Token、长文本需要多长超时。

因此适配器只做最小的事：

- 发送标准请求；
- 解析 `choices[0].message.content`；
- 对 HTTP 错误、空回答、超时、取消做明确分类；
- 不把厂商 SDK 和业务逻辑混在一起。

Provider 预设只是“自动填充”，不是硬编码。用户可以改 Model ID、Base URL 和 Key 引用，以适配不同区域、不同套餐和不同部署方式。

### 第四阶段：Judge 与计分

Judge 使用固定协议 `edueval-judge-v0.1`，输入是：

```text
原 Query + 本题 Rubric + Critical Errors + 匿名候选回答
```

Judge 必须为每个维度返回整数 0/1/2、证据和理由。Host 不信任 Judge 给的总分，而是用 Rubric 权重重新计算：

```text
总分 = Σ(weight × score / 2)
```

Judge 返回的结构不合法、维度缺失、分数越界，都会记为失败，而不是悄悄按 0 分处理。

### 第五阶段：界面与交互

界面分成五个区域：

```text
01 Model Generation
02 Model Responses
03 Evaluation
04 Results & Report
05 Human Review
```

先让主流程跑通，再补看板和盲评。最后做了一轮 UI 清理，删掉所有灰色说明性小字，让页面从“解释型界面”变成“操作型界面”。

### 第六阶段：测试与真实验证

自动化测试覆盖了：

- Benchmark 结构与权重；
- 计分公式与 Judge 校验；
- CSV 解析；
- 配置归一化与密钥不落盘；
- Mock 全流程、持久化、取消/继续；
- 本地 HTTP 真实适配器；
- 10 题 × 3 模型 = 30 份回答与 30 份评分。

此外用 Playwright 在真实 DSH Web UI 中验证了主面板、模型配置、Mock 运行、看板和人工盲评。真实厂商调用也做过单独验证，包括成功、余额不足、超时和思考模型空回答等异常路径。

### 第七阶段：打包与分发

插件没有运行时 npm 依赖，也没有构建步骤。最终以 tgz 分发：

```bash
dsh plugin --profile desktop add /path/to/dsh-plugin-edueval-1.0.0.tgz
```

重启 DSH 后即可从侧边栏进入。安装、升级、卸载和数据保留策略都写进了 README。

## 五、开发中遇到的典型问题

### 1. Host/Client 边界不是形式主义

最初很容易把 Key 状态、模型身份或评分逻辑放到浏览器里，图一时方便。但这样一来，盲评和密钥安全都失去意义。

最终所有敏感状态都留在 Host，浏览器只拿它需要看到的字段。

### 2. “Key 已配置”不等于“Key 可用”

凭据引用、保存时机、是否记住 Key，是三个不同的问题。用户输入 Key 后没有点保存，或者没有勾选记住，Host 重启后就会失去它。

后来把保存动作做成显式按钮，同时让“测试连接”和“运行评测”自动保存当前输入，并在卡片上直接显示 `Key 已配置 / Key 未配置 / 未保存`。

### 3. 不同厂商的“OpenAI 兼容”并不完全一样

Base URL 要不要带 `/v1`、模型 ID 是否区分大小写、思考模型会不会把 Token 全花在 reasoning 上、长文本请求多久超时，这些都不是协议层能统一解决的。

所以插件保留可编辑字段，并在连接测试中避免发送过小的 `max_tokens`；对长文本任务提供更长的超时，同时允许用户选择更适合长文生成的模型。

### 4. 失败必须被看见

超时、限流、余额不足、空回答、Judge JSON 不合法，最终都可能表现为“没有结果”。

系统没有把失败当作 0 分，而是保留错误、覆盖率、失败案例和 Critical Error。这样用户能区分“模型答得差”和“模型根本没答”。

### 5. 评测集要能替换

内置 Benchmark 从最早的 30 题版本，替换为当前的 10 题 v0.2 版本：5 道教案生成 + 5 道课件大纲，每题 6 项 Rubric，权重合计 100。

题目是评测的一部分，不是插件的装饰。替换题目时，版本号、Benchmark ID、校验脚本、测试和文档都要一起更新。

## 六、边界与未来

EduEval Studio 不是标准化行业基准，也不承诺用一个分数决定模型优劣。

当前 10 题数据是任务提供方提供的合成评测集，样本量小，尚未经过一线教师的大规模验证，也没有做题目区分度分析。LLM Judge 的结果也会受模型版本、提示词和评分标准影响。

它更适合回答这样的问题：

- 在同一批题目和同一套 Rubric 下，这几个模型的表现差异在哪里？
- 失败和 Critical Error 集中在哪些维度？
- 人工判断和 Judge 判断在哪些题上分歧最大？
- 换一个模型或换一版 Rubric，结论是否稳定？

后续可以继续做的方向包括：扩大并验证 Benchmark、引入多 Judge 交叉评分、支持流式长文本、增加人工评分校准、补充更细的成本与延迟统计，以及把评测结果接入更多的教学资源生产流程。

## 七、结语

EduEval Studio 的核心不是“让模型写出一份教案”，而是让“模型写得怎么样”这件事变得可比较、可解释、可复查。

它把评测拆成题目、生成、评分、人工复核和报告几个独立环节，把每个环节的状态留在本地，把密钥和模型身份留在 Host，把界面压缩到只剩必要信息。

这也是这个插件最重要的设计选择：**不追求看起来复杂，而追求每一次结论都能回到证据。**
